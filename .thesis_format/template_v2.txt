摘  要
随着汽车产业不断往“电动化、网联化、智能化、共享化”这几个方向深入发展，车载信息娱乐系统，也就是常说的IVI，正慢慢变成智能座舱里最核心的一块。本文的工作是依托HarmonyOS的分布式架构，设计并且实现了一套车载信息娱乐系统。针对传统方案里生态相对封闭、交互操作比较冗余，还有多台设备之间不好协同这些比较头疼的问题，我们试着提出了一种“分布式内核加上极简交互外壳”的设计思路。
从功能上看，这个系统主要想把导航、多媒体、车辆监控和多设备协同这四个大模块都整合到一起；在交互这一层，则是通过构建一个全局的非阻断式快捷交互机制，来让驾驶员操作时不用那么分心，认知负荷能低一些。数据方面，依靠WebSocket这条双向同步通道，手机跟车机之间能够做到实时协同，把那种“上车接着听，下车继续看”的连贯体验给复现了出来。最后的测试结果也表明，不管是功能上的完备程度，还是性能响应以及多设备协同时的稳定性，这套系统都达到了先前设定的预期标准，算是给国产操作系统在智能座舱这块的应用，提供了一个可以拿来参考的范式。

关键词：HarmonyOS  车载信息娱乐系统  分布式架构  非阻断交互  跨端协同

Abstract
With the deep development of the automotive industry towards "electrification, intelligence, and sharing," the In-Vehicle Infotainment (IVI) system has become the core of the smart cockpit. Based on the distributed architecture of HarmonyOS, this paper designs and implements an advanced IVI system. Addressing the structural issues of traditional systems, it proposes the concept of a "distributed kernel + minimalist interactive shell."
The system integrates four modules: navigation, multimedia, vehicle monitoring, and multi-device collaboration. It constructs a global non-blocking interaction mechanism to reduce driver distraction. At the data level, it achieves real-time synchronization between phones and cars via WebSocket, providing a seamless "start on phone, continue on car" experience. Test results demonstrate that the system meets expectations in functionality, performance, and stability.

Key words: HarmonyOS  IVI  Distributed Architecture  Non-blocking Interaction  Cross-device Collaboration

第一章 绪论
1.1 课题研究背景及意义
21世纪以来，汽车产业正以一种前所未有的速度，朝着“电动化、网联化、智能化、共享化”这几个方向持续演进，汽车的形态边界也在这个过程中被大大拓宽了，它早就不再只是一个承担位移功能的交通工具了，而是慢慢变成了一个拥有高算力、强连接和多模态交互能力的移动智能终端。在这样的产业变化里，车载信息娱乐系统，也就是常说的IVI，作为人机交互（HMI）的关键载体，担负着导航、娱乐、车况显示还有多端协同这些重要职能，它的智能化程度，已经成为衡量整车智能座舱体验的一个主要指标，并且在很大程度上影响着用户的驾乘满意度和对品牌的忠诚度[1]。
不过，随着车主使用的频率和应用的复杂度都在快速上升，传统的车载信息娱乐系统在面对越来越丰富的用车场景时，慢慢就暴露出了三个不太好绕过去的结构性短板。第一个是生态封闭的问题，早期那些基于嵌入式实时操作系统（比如QNX）构建的车机，虽然稳定性不错，但能用的应用资源一直很有限；后来成为主流的Android Automotive OS，虽然靠着成熟的移动生态在应用数量上占了优势，却也把宏内核架构资源开销大、长期运行后流畅度容易下降这些问题一并继承了过来[2]。第二个是交互层级冗余，现有的系统大多还在延续桌面端或者平板端那套“层级菜单加页面跳转”的交互方式，这和驾驶员在行车时那种“只能短时间看屏幕、注意力不能多分配”的认知特点不太合拍，结果就是，处理次要任务时的操作步数和视线离开路面的时间，常常很难控制在安全的范围里面[3]。第三个则是多设备协同上的困难，当下主流的车机互联方案，主要还是依赖应用层的投屏协议，手机和车机在数据层面缺少深度的同源，像“上车断连、下车切歌”这种体验上的断裂感就经常会出现[3]。这些问题都表明，车载信息娱乐系统下一阶段的升级，得从底层架构和交互范式这两个方向同时动手才行。
在这样的产业背景下，华为推出的HarmonyOS操作系统，给出了一个能对上号的解决思路。HarmonyOS采用了一种基于微内核的分布式架构，通过分布式软总线这项技术，把多个智能终端虚拟成一个统一的大家说的那种“超级终端”网络，这里面的每一台设备，既是这个网络里一个独立的节点，同时也可以看作是其他设备在能力上的延伸[4]。这样一个架构，从理论上来讲，是能够把“应用上下文”从一台设备没有感觉地搬到另一台设备上的，这就从根本上突破了传统车机硬件那些物理上的限制[5]，而且，它通过统一的分布式数据服务，给多端数据同源提供了一个系统层面上的支撑[6]。与此同时，HarmonyOS提供的ArkTS加ArkUI这一套原生开发的范式，把声明式UI跟响应式数据驱动当作核心，也就是说，跟以往那种命令式的开发比起来，这种方式能更高效地做完界面性能优化和跨不同尺寸屏幕的适配工作，这也给车载场景下那些复杂、需要同时处理的业务打下了一个还不错的工程底子。
综合上述产业需求与技术机遇，本课题以 HarmonyOS 为底层平台，围绕"分布式的内核 + 极简的交互外壳"这一总体设计理念，研究并实现一套面向智能座舱场景的车载信息娱乐系统。系统在功能层面整合导航、多媒体、车辆监控与多设备协同四大核心模块；在交互层面构建系统级的全局非阻断式快捷交互机制，使核心业务的切换不依赖于层级跳转；在数据层面通过应用层等效的发布-订阅同步通道实现手机与车机的双向数据同源，从而对开题报告所提出的三大方向——架构整合、交互重构与跨端数据同源——形成完整工程闭环。
本课题的研究意义，可以从理论和实践这样两个维度来谈。在理论这一层上，本研究主要是想对基于微内核的分布式操作系统在垂直应用场景下的工程理论，做一些丰富和补充，具体来说，就是通过对跨端发布-订阅同步通道进行语义建模，给异构网络环境下多端数据一致性的工程实现，整理出一个能够重复使用的范式；与此同时，再结合车载高分辨率环境里声明式UI的渲染与状态管理实践，也能为后面相关的学术研究，提供一些方法论上的参考。
在实践层面，本研究的工程价值同样显著。第一，所设计的导航、多媒体、车辆监控与多设备协同四大模块覆盖了驾驶员在行车与驻车两类场景下的主要高频需求，具备直接的应用价值；第二，所提出的全局非阻断式快捷交互机制将核心任务的切换路径压缩为常驻全局层的一次轻量操作，有助于降低驾驶员在次要任务上的认知负荷，对提升行车安全具有积极意义；第三，所实现的跨端协同模块在应用层完整复现了 HarmonyOS 分布式协同的核心语义，可为车企在不依赖原生分布式硬件环境的前提下落地"上车续看、下车续听"等连续性体验提供可参考的技术原型，亦可为国产操作系统在智能交通领域的进一步推广积累工程经验。
1.2 国内外研究现状
1.2.1 车载信息娱乐系统的演进与发展现状
车载信息娱乐系统的演变，一直是跟汽车产业智能化的脚步绑在一起的。从最早那种主要是独立机械按键和简单收音模块的车载娱乐终端，到中期开始用嵌入式实时操作系统（RTOS）来搭建中控仪表，再到现在这种面向智能座舱场景、集成度很高的交互平台，IVI在硬件的样子、软件的架构还有功能能覆盖到的范围这三个方面，都发生了很明显的转移。孙德强他们曾经对车载信息娱乐系统的大致发展过程做过一个梳理[1]，给出的看法是，目前的IVI已经从一个车厂的“附加配置”，变成了整车智能化里的一个核心部分，整体上呈现出“中控屏幕越做越大、系统走向平台化、功能搬到云端、交互方式变成多模态”这样的大方向。
在这个大方向的推动之下，研究IVI的关注点，也开始从单一终端上怎么把功能做出来，转向了在智能网联这个大背景下，怎么搞系统级的集成跟创新。史航玮在专门研究智能网联汽车环境下的IVI时提到[2]，下一代的IVI，光有把本地业务高效跑起来的能力已经不够了，它还得在车、机、人这几端之间的协同，车跟云的数据交互，还有人机交互的安全性这些方向上，去扮演更复杂的角色，这样一来，对底层操作系统的分布式能力，也就提出了比原来高得多的要求。另一边，张俊仪他们，则是从IVI软件项目具体怎么开发这个角度切入，给出了一套从需求分析、架构设计再到模块实现和集成测试的完整工程方法[3]，这给IVI项目在工业化交付时怎么做得更规范，提供了一条可以参考的路子。
综合上述研究可以看出，国内学界对 IVI 的研究关注正在由"功能堆砌"转向"系统集成与体验创新"，这与本课题所提出的"将分布式内核与极简交互外壳有机结合"的设计理念保持一致。
1.2.2 HarmonyOS 与分布式协同关键技术研究
HarmonyOS 作为面向万物互联场景的分布式操作系统，其与传统单设备操作系统最显著的差异在于将"多设备"作为系统设计的一阶抽象。黎芷杉对鸿蒙操作系统在分布式智能终端管理中的应用进行了系统讨论，指出 HarmonyOS 通过分布式软总线、设备虚拟化与统一身份认证三项核心能力，实现了对手机、平板、车机、可穿戴设备等异构终端的统一接入与协同调度，使应用开发者可以"以一台设备的视角去使用多台设备的能力"。
在跨端协同具体怎么实现的技术这一块，龙军他们曾经对HarmonyOS的分布式流转能力，在应用开发这个层面做过一些研究[5]，里面分析了任务搬移、状态迁移还有界面续接这些到底是怎么一回事，并且指出来，分布式流转本质上靠的是一种基于发布-订阅跟状态同步的应用上下文搬移机制。这个看法，对本课题来说有挺直接的指导作用，也就是说，本系统并没有去依赖鸿蒙原生的分布式API，而是借鉴了这个思路，在应用层自己搭了一个效果差不多的发布-订阅式同步通道。同时呢，龙军他们在另一项研究里头，又专门针对HarmonyOS的分布式数据服务做了比较深入的分析[6]，指出这个分布式数据服务，它的核心特征就是让应用完全感觉不到的最终一致性，而且是通过统一的命名空间和同步策略，把底层的网络细节都给盖住了。这项研究呢，就给本系统在跨端数据同源这块的设计，提供了一个语义层面上的参考，所以，本课题最后是选了服务端集中做持久化，再配合上WebSocket双向广播这么一种组合方式，从功能上等效地复现了“最终一致性”这种同步的语义。
1.2.3 鸿蒙在垂直应用领域的工程实践
在与本课题最相关的工程对照层面，刘丹等人针对基于鸿蒙系统的分布式音乐播放器进行了完整的设计与实现研究，重点解决了多终端环境下的设备发现、播放状态同步与跨端续播等关键问题。该工作从工程层面验证了鸿蒙分布式技术在音视频应用中的可行性，但其讨论范围仅限于音乐这一单一业务，缺少对导航、车况、联系人、短信等多类型业务统一协同的工程实证。本课题在此基础上，将该范式向上扩展至车载场景，将分布式协同思想应用于音乐、导航续接、联系人、短信等多类业务，并由全局非阻断式交互层进行统一调度，从而填补了现有研究在"多业务统一协同"层面的工程空白。
1.2.4 车载界面设计与系统支撑技术研究
在车载HMI的视觉跟认知这个层面，欧阳武旻他们曾经对车载信息娱乐系统的界面美学设计，做过一套比较系统的研究[8]，从信息怎么分层、视觉密度怎么控制、动效节奏怎么把握这些方面，总结出了一套车载界面得在“美学表达”跟“驾驶安全”之间去找平衡的设计准则，并且特别强调了，界面上信息怎么呈现，主要应该是先为驾驶这个任务服务，而不是为了视觉上搞得好看。这个研究，算是给本系统在第三章详细设计那部分，搞关键界面的线框图还有定配色方案这些事儿，提供了一个理论上的底子。
在持久化层选型层面，翟凌云对 MySQL 数据库在分布式系统架构中的应用进行了讨论，指出 MySQL 凭借成熟的事务模型、丰富的索引机制以及较低的运维成本，仍然是中等规模分布式架构下关系型持久化的首选方案。本系统据此选择 MySQL 8.x 作为后端持久化引擎，并在分布式协同场景下通过统一的写路径将"REST 写库—WebSocket 推事件"作为标准范式，从而在保留单点持久化优势的同时获得跨端实时同步能力。
在生态发展这一块，李娟等人对鸿蒙系统应用开发微专业的建设路子做过探索性研究[10]，里面提到，鸿蒙生态正在通过产业跟高等教育的协同推进，慢慢形成一套完整的人才培养和软件供应链体系，这个趋势也说明了，国产操作系统在车载、智能终端这些垂直领域落地工程的条件，已经越来越成熟了，而本课题呢，正是在这样的生态大背景下，做的一项工程实证研究。
综合上述四个方向的研究现状可以看出：现有工作在车载信息娱乐系统的演进趋势、HarmonyOS 的分布式核心机制、鸿蒙在单一垂直业务的工程实践，以及车载 HMI 与系统支撑技术等方面均已有较为充分的积累，但仍存在三方面待解决的不足：其一，缺乏将导航、多媒体、车辆监控与多设备协同四大模块在统一架构下整合的综合性工程实证；其二，针对驾驶场景定制的、能够实现非阻断式快捷操作的系统级全局交互组件研究尚不充分；其三，分布式协同的实证研究多集中于单一业务，跨多业务的端到端数据同源工程范式尚未形成。本课题正是面向上述三类空白进行的针对性研究。
1.3 论文主要工作
围绕基于 HarmonyOS 的车载信息娱乐系统这个核心命题，本论文主要做的工作，可以归纳成下面四个方面。
第一，是开展了车载信息娱乐系统的需求分析和总体架构设计。具体来说，是先对行车态和驻车态这两类场景下，不一样的交互优先级做了一个分析，然后明确了系统都有哪些功能性的需求，比如导航、多媒体、车辆监控还有多设备协同这些，以及一些非功能性的需求，像启动响应快不快、界面流不流畅、跨端同步的延迟、还有数据安全这类。在这个基础上面，设计了一个从上到下的六层垂直分层架构，同时规划了两条并行的通信链路，一条是端和云之间的通信架构，另一条是跨端协同的同步通道；并且靠着一套统一的状态管理跟服务接口，把业务逻辑和界面渲染给彻底解耦开了。
第二，是设计并且实现了一个全局性的、非阻断式的快捷交互控制体系。这个体系可以算是本课题的一个核心创新点了，它用的是一种“覆盖层加上全局事件总线，再加上智能布局”的复合机制，这样一来，用户就不需要先退出导航这类主任务的上下文，直接通过屏幕边缘那些一直停在那里的常驻控件，就能很快地把媒体控制、协同状态、TTS 公告这些次要任务的面板给唤出来，等操作做完了呢，面板又会自动收回去。靠着这种机制，核心任务的切换路径就被压缩成了全局层上一次很轻量的操作，驾驶员在处理那些次要任务时的认知负荷，还有视线偏离路面的时间，都跟着明显降了下来。
第三，是设计并且实现了一个基于发布-订阅模式的跨端协同同步通道。这个通道呢，没有去依赖 HarmonyOS 原生的分布式硬件环境，而是借鉴了分布式软总线跟分布式数据服务的那套语义模型，在应用层自己搭出来的；它把服务端的 SyncHub 当做核心，用 WebSocket 长连接来作为传输的通道，然后再拿 MySQL 做集中持久化来当状态的基线，这么三段式的一个同步通道。通过这个通道，把“设备发现、状态广播、事件订阅、双向同步”这四种最核心的协同语义，都完整地复现了出来；并且在音乐续接、导航续接、联系人协同，还有短信协同这四类业务上头，都做了端到端的工程实证。
第四，是把导航、多媒体跟车辆监控这三个基础的业务模块，都集成到了一起并且给实现了。导航模块这一块，是基于 WebView 来集成高德地图的开放接口，能够提供高精定位、POI 检索、路径规划，还有历史记录的管理功能；多媒体模块呢，是基于 HarmonyOS 的 AVPlayer 来搭建了一个本地的音频播放引擎，同时还实现了 LRC 歌词的解析，以及一种靠着固定容器位移来实现的卷帘式高亮算法；车辆监控模块，是把电动车的那个数据模型当做对象，去构建了一个双频采样的车辆状态模拟器，它覆盖了车速、动力电池的 SOC 和 SOH、胎压、温度、行驶里程还有安全评级这些核心的指标，并且通过 ArkUI 里的 Gauge 和 Progress 这类组件，做出了动态的仪表盘可视化效果。
上述四方面工作共同构成了本课题在"分布式内核 + 极简交互外壳"设计理念下的完整工程闭环，并在第五章通过功能测试、性能测试与协同延迟测试三类实验对系统的有效性进行了实证验证。
1.4 论文组织结构
本论文共分为六章，各章主要内容如下：
第一章 绪论。 阐述课题的研究背景与意义，分析国内外车载信息娱乐系统与 HarmonyOS 分布式协同技术的研究现状，归纳现有工作的不足，并据此明确本论文的主要工作内容、技术路线与组织结构。
第二章 系统分析。 在对 IVI 业务场景进行场景化拆解的基础上，从技术、经济与社会三个维度论证课题的可行性；进而以用例图为核心工具，对系统的功能性需求与非功能性需求进行结构化建模，为后续的架构设计提供输入。
第三章是系统设计，内容分成了概要设计、功能模块结构设计、数据库设计还有详细设计这么四个部分。概要设计这部分，主要是把系统的总体分层架构、端云通信架构，以及跨端协同同步通道的设计给出来；功能模块结构设计呢，就是从上往下，把五大模块各自内部的子结构给理清楚；数据库设计的话，给出了全局的E-R模型，还有每张数据表的逻辑结构；详细设计这一块，则是针对全局交互路由引擎、分布式数据同步机制、非阻断式交互调度，再加上关键的界面线框这四类比较核心的环节，拿出了具体的设计方案。
第四章是系统实现，大体上是顺着关键算法、分布式协同和基础业务这三条线，把系统实现里那些核心的细节讲了一遍，重点说明了这么几块：全局非阻断式快捷交互、歌词时间轴的解析与翻页对齐、跨端续接用的状态机、设备在线状态的维护，还有WebSocket这个双向同步通道，再一个，就是导航、多媒体、车辆监控这三大业务模块到底是怎么做出来的。
第五章是系统测试，这章会先把测试的目的、测试环境跟测试方法做个介绍，然后，依次去完成功能测试、性能测试还有协同测试，完了之后，再对测试出来的结果做一次多维度的分析，看看系统在功能上是不是都完备、运行性能好不好、跨端同步的质量怎么样，也就是验证一下它有没有达到前期想要的效果。
第六章 结论。 对本课题的工作进行总结，分析研究成果在社会、经济与文化层面的关联与价值，归纳论文的主要创新点，并指出当前工作的不足与未来可能的扩展方向。

1.5 本章小结
本章作为论文的绪论部分，首先从汽车产业向"电动化、网联化、智能化、共享化"演进的产业背景出发，阐明了车载信息娱乐系统作为智能座舱核心交互载体的研究价值，并指出现有 IVI 在生态封闭、交互层级冗余与多设备协同困难三个方面的结构性短板；其次，结合国内外学者在 IVI 演进趋势、HarmonyOS 分布式协同技术、鸿蒙在垂直应用领域的工程实践以及车载界面与系统支撑技术等方向的研究成果，归纳了现有研究在"多模块统一架构整合""驾驶场景定制化交互""端到端数据同源工程范式"三方面的不足；最后，明确了本课题的四项主要工作与论文的整体组织结构。本章为后续各章的需求分析、系统设计与系统实现提供了研究背景、问题定位与方法论支撑。
第二章 系统分析
2.1 业务分析
车载信息娱乐系统的核心用户，是在行车和驻车这两种不同的运行状态下面，驾驶员自己还有跟着一起乘车的乘客，它这个业务形态呢，跟桌面端、移动端那种是有根本上的不一样的。第一点，就是操作的人，需要在驾驶这个主要任务和各种次要任务之间，来来回回地、很快地切换，每一次的交互，都必须控制在很短很短的时间里面完成；第二点呢，是系统要承载的那些业务种类，跟着场景的不同而分得特别清楚——开车的时候，强调的是“少看、少按、反应要快”，车停下来的时候呢，强调的又是“信息要给足、操作可以做完整”；第三点，这个系统得在一台设备上面，同时干导航、多媒体、车况监控、多端协同这些乱七八糟、性质不太一样的活儿，总体上看呢，它那样子大概是介于一个工具类应用和一个信息门户中间。所以呢，本系统在做业务分析的时候，就决定用“场景-角色-模块”这么一条三维映射的线作为主干，从上往下地把业务边界跟交互优先级给理一理。
2.1.1 运行场景分析
依据驾驶任务的状态差异，本系统将全部业务场景划分为行车态与驻车态两类。
在行车态的时候，驾驶员主要的认知这块的带宽，基本都被驾驶这个任务给占去了，所以那些次要的任务就得同时满足三个约束：视线离开路面的时间要短、操作的步数要少，还得能被打断之后又能给接回去。这个场景下面比较典型的业务，包括：正在做的导航里头，对路径那种实时的跟踪、媒体那块需要的暂停、切歌和调一下音量、对车况那些关键指标的一个“瞥一眼就行”式的查看，还有接收从手机那头传过来的续接请求之类的东西。在这个场景下面，系统是要拿那种非阻断式的快捷交互，来当成默认的交互方式，具体说呢，就是所有的次要任务，都靠屏幕边上那种一直悬在那儿的控件，或者是全局的那种覆盖层给唤出来，而导航地图这种属于主任务的东西呢，就一直在那儿保持能看见的样子。
到了驻车态的时候，驾驶员就变成一个普通的、坐在那儿慢慢用的用户了，认知这块的带宽富余得很，业务的重点，也就跟着转到把信息充分给显示出来，还有做一点细致的、个性化的设置上面去了，比较典型的业务呢像什么：看一下最近七天的行驶里程、管一管自己收藏的地点、浏览那些协同过来的联系人和短信、发起一下把音乐或者导航续接到车上的动作，还有查看同步日志这些。在这个场景下面，系统就应该用一种能把信息给充分展示出来、同时又有层级组织的方式，来把内容给呈现出来，也允许用户在车停着的时候，搞一些更复杂点的、跨页面的导航和设置这一类的操作。
2.1.2 角色分析
用刚才的场景分析作基础，本系统总共梳理出来三类会参与进来的角色：
(1) 一个呢，是驾驶员（Driver）。这个是系统最主要的使用者了，开车的时候，用系统搞导航、控制媒体、看看车况、还有就是听语音播报这些个核心的事儿；等车停好了，又会用到账号管理、收藏夹的维护、协同方面的配置这些个扩展起来的功能。驾驶员这个角色，同时也是整个系统功能里头，对响应延迟和交互搞起来是不是足够简单直接，那个感觉最灵敏的人。
(2) 再一个呢，是手机端的用户（Phone User）。这多半就是驾驶员自个儿了，只不过这时候，他是拿着手机这个设备，来一块儿干系统协同上的事情。这个角色主要管的事儿，是在手机那边维护联系人、音乐库还有导航里收藏的点，然后呢，在离开车子或者要上车这么一个过程里头，从手机那边主动发起一个跨端续接的请求，在跨端数据要保证是同一个源头这条链路上，他是那个起头的一方。
(3) 还有一个呢，是后端系统（Backend）。这个算是一个次要点的、参与进来的系统侧的角色，要干的事情有，搞定账号的认证、把数据给存盘持久化、在中间帮忙中转一下同步事件、还有把状态给广播出去这些。这个角色，倒不是直接对应现实里头哪个活生生的人，但是在画用例模型的时候，是作为外部的一个参与者给存在的。

2.2 可行性分析（技术 / 经济 / 社会）
2.2.1 技术可行性
从技术实现层面，本课题所依赖的核心技术栈均已达到产业成熟度。第一，HarmonyOS 提供了完整的 ArkTS + ArkUI 原生开发范式与相对完善的开发者工具链（DevEco Studio），为车载大屏应用的研发提供了稳定的平台支撑；黎芷杉等人的研究已从分布式智能终端管理的角度论证了该平台在多终端场景下的工程可行性。第二，系统所选用的 WebSocket 长连接、REST API、MySQL 数据库等通用软件技术已在互联网产业中经过长期验证，翟凌云在对 MySQL 在分布式系统架构中的应用研究中指出，MySQL 在中等规模分布式场景下仍具备良好的稳定性与工程可控性。第三，高德地图开放平台提供了成熟的 Web 地图 JavaScript API，可满足系统在路径规划、POI 检索与可视化渲染上的需求。第四，本课题的跨端协同技术路线已在刘丹等人的分布式音乐播放器研究中得到初步工程验证，本系统在其基础上将该范式扩展至多类型业务，具备明确的工程基线。综上，本系统所有关键技术均具备成熟的开源或商用实现，技术可行性成立。
2.2.2 经济可行性
单从经济成本这个角度来看，本课题在研发跟上云部署这块的开销，都是能控制得住的。先说开发成本，系统用到的那些东西，像开发工具 DevEco Studio、Node.js 运行时，还有 MySQL 的社区版、开源的 WebSocket 跟 Express 框架这些，全都是免费或者社区开源出来的版本，并不会有额外的授权费用要掏；高德地图那个开放平台呢，正常用量底下，也提供了一定额度的免费使用空间，拿来覆盖毕业设计阶段的调试和演示需求，是足够的了。然后是部署这一块的成本，后端服务对服务器硬件的要求并不高，一个单节点 2C4G 的云服务器，就能应付得来本课题涉及的这种并发规模了；数据库也可以跟后端布在同一台机器上，这样还能把运维的费用再往下压一压。再往后看维护成本，系统用的是那种模块化的分层架构，不同的业务模块之间，都靠统一的接口连在一起，以后如果想要往上加新功能，或者把某些部分替换掉，比如说接进真实车辆的 CAN 数据这种情况，也就只需要在原来定好的接口层上，做一点有限的改动就行，长期来看维护这边的花销也是可控的。把这些都拢到一块儿来看，本系统的研发跟后续运维，在经济这一头都是站得住脚的。
2.2.3 社会可行性
从社会需求这个层面来看，本课题是既有现实应用上的价值，在行业里也算能起到一点引领的意思。需求这块，孙德强等人[1]和史航玮[2]的研究都指出来，智能座舱现在已经是整车智能化里一个很关键的竞争点了，驾驶员对那种“极简操作、多端连续体验”的期待一直在往上走，这跟我们系统提出的“非阻断式快捷交互加上跨端数据同源”的设计目标，贴合得是相当紧的；安全上呢，本系统一直就是把驾驶任务放在最高优先级的位置，想着靠把次要任务造成的视线偏离时间给压短，来把驾驶分心的风险降下去，这个思路跟国内外那些研究驾驶安全与防分心的主流方向，是能合在一块的；到了产业这一块，李娟等人[10]的研究里有说，鸿蒙的生态正在靠着产业跟高校这两头一起使劲，慢慢形成一套完整的人才还有软件供应链，而本系统作为这个生态底下的一个车载应用方面的工程验证，多少也能帮着国产操作系统在往垂直领域落地的时候，提供一个可以拿来参考的工程样例。所以整体上看下来，本课题在社会这个层面，可行性是挺充分的，积极的正面价值也是有的。

2.3.2 非功能性需求分析
除上述功能性需求外，系统在性能、可靠性、易用性、安全性与可扩展性等方面还需满足以下非功能性需求。
(1) 在性能上，要求冷启动时间不超过3秒，首屏渲染控制在800毫秒以内，页面跳转也得在300毫秒之内完成，日常运行的帧率要大于等于55FPS，跨端同步那个端到端的延迟，在P95这个指标下，也要能卡在300毫秒以下
(2) 可靠性这边，WebSocket连接一旦断开，得能自己重新连上，两次重连之间的最大间隔不能超过30秒，后端往库里写数据，万一失败了，也必须返回一个明明白白的错误码，不能让客户端那边静悄悄地就把数据弄丢了，整体程序的崩溃率，要压在0.1%以内
(3) 易用性上，在行车的状态下，所有核心任务的操作步骤数，最多就2步，任何一次次要任务带来的视线偏离时间，都得合乎驾驶分心方面的安全约束，界面上信息的呈现呢，也要照着“层级清楚、视觉密度不多不少”的设计原则去走[8]
(4) 安全这块，账号密码用的是bcrypt加盐的方式存着，接口的权限验证是基于JWT令牌的，而且令牌过期了还能自动刷新，WebSocket在广播事件的时候，会按照userId这个字段来做过滤，防止一个账号的信息泄露到另一个账号那里去
(5) 可扩展性上，系统整个搭的是一个六层的垂直分层架构，业务模块彼此之间是拿接口耦合的，而不是绑死在具体的实现上，后端的REST接口也把版本号放在了路径里，像/api/v1/*这样，方便以后接口慢慢地往下改，协同用的那条同步通道，被单独封在一个叫CollaborationSyncSocketService的服务里面，算是提前留好了将来往HarmonyOS原生分布式API上迁移的这么一个能力。
2.4 本章小结
这一章呢，主要是围着系统的需求，从头到尾做了一遍分析。业务分析这块，是从行车和驻车这两种不同的运行场景开始往下捋的，把驾驶员、手机端用户还有后端的系统，这三类会参与进来的角色给挑了出来，然后把系统要干的那些事儿，分成了账号身份、导航、多媒体、车辆监控，再加上多设备协同，总共五大类，里头包含18项核心的业务。可行性分析呢，是从技术、经济，还有社会这三个角度，去说了说这个课题为什么能做，算是确认了要倚仗的那些关键技术，现在都已经挺成熟了，研发和后面维护的钱也都能控制在手里，而且本身还带着一些积极的产业跟社会方面的价值。到了需求分析那里，是用UML用例建模当作主要的工具，弄了一张系统总体的用例图出来，就是图2-1里头那个，跟着又挑了里头比较有代表性的四个核心用例，也就是UC11的全局快捷控制、UC04的发起路径规划、UC17的音乐跨端续接，还有UC02的用户登录，给每个都配上了一张完整的用例描述表；同一时候，还从性能、可靠性、易用性、安全性跟可扩展性这五个维度，把系统那些非功能性的需求也给理了一遍。这么一趟分析下来，得出来的结果，算是给第三章的系统设计，把前面要输入的条件和后面要受的约束，都比较清楚地交了过去。
第三章 系统设计
3.1 概要设计
3.1.1 系统总体分层架构（架构图）
系统的总体架构以"层次清晰、职责单一、单向依赖"为基本设计原则，自顶向下采用六层垂直分层架构，各层之间通过明确定义的接口进行交互，上层不依赖下层的具体实现细节。系统总体分层架构如图 3-1 所示。
图 3-1 系统总体分层架构图
center-7480935
第一层为用户层，包含驾驶员、手机端用户与车机端用户三类终端使用者，是系统所服务的全部自然人主体。第二层为应用层，由导航、多媒体、车辆监控、协同总览、登录与个人中心五大功能模块及其子页面组成，并叠加贯穿整个应用层之上的全局非阻断式快捷交互层。第三层为业务服务层，包含 GlobalAnnouncerService（全局事件总线）、CollaborationViewModel（协同视图模型）、RealAudioPlayerService（音频播放服务）、RealMusicBridgeService（歌词同步桥）、AppStorage（全局响应式状态）以及 Router（页面路由）等应用进程内单例服务，承担应用层之下的领域业务封装。第四层为同步通信层，集成 REST 客户端 CollaborationApiService、WebSocket 客户端 CollaborationSyncSocketService、高德地图 WebView 桥与 JWT 鉴权客户端，对外屏蔽通信细节。第五层为后端服务层，基于 Node.js 与 Express 构建，包含若干业务控制器（账号、协同、媒体、导航等）以及作为本系统同步事件中转中枢的 WebSocket Server CollaborationSyncHub。第六层为数据持久化层，基于 MySQL 8.x 构建，包含用户、收藏、导航历史等业务表与协同模块的 8 张专属表。
这个分层架构，拆开来看的话，在工程上能带来三个比较重要的好处。首先，层次之间那种单方向的依赖关系，让系统的可维护性有了保证，也就是说，随便哪一层自己在内部做什么改动，对挨着它的那一层来说，都是透明的、看不见的。然后呢，那个全局快捷交互层，它是横着穿过了应用层上面，这么一来，就给本课题那个“非阻断式交互”的创新点子，在系统这个层面提供了一个实实在在的安放位置和支撑。再就是，SyncHub这个负责中转同步事件的中枢，加上 collaboration_active_devices 这张管设备在线状态的表，这两个东西合在一起，就成了本系统做跨端协同最核心的那个枢纽部分，等于说，是给“跨端数据同源”这个创新点，铺好了一个最底层的、基础性的支撑。
3.1.2 前后端通信架构
这个系统要处理的是手机、云端还有车机这三方之间怎么通信的问题，所以整体上用的是一种把端云通信，跟经云端中转的跨端协同，这两条链路并排着跑的设计。
在端云通信这块，手机端跟车机端，都是当成对等的客户端节点来用的，它们会通过一个基于 HarmonyOS 系统模块 @ohos.net.http 封装出来的统一 REST 网关，去跟后端做那种请求-响应的业务交互；而后端这边，是在 Node.js 跟 Express 框架上搭起来的，对外的接口都弄成了资源化的形式，看着像是 /api/v1/{collaboration|navigation|media|auth}/* 这个样子，同时呢，还用了 JWT 令牌在请求头里就把无状态的身份认证给做了。像联系人、短信、音乐元数据，还有导航历史等等所有这些业务对象，它们的增删改查操作，全都顺着这个 REST 通道，往下交到后端，再由后端统一给持久化到 MySQL 数据库里头去，这么一来，从最根本上，就把两端数据的一致性问题给管住了。
到了跨端协同这一头，本系统倒是没有去用那种传统的应用层投屏，或者设备之间直接点对点连起来的方案，而是给弄成了一个靠云端中转的发布-订阅模式，就是说，手机和车机，都会通过 WebSocket 长连接，去订阅后端那个同步事件中转服务 CollaborationSyncHub，由这个服务来负责事件的路由、过滤还有广播这一摊子事，这样做，也就避开了在跨网段、跨子网这种环境下，要点对点去建立连接比较难搞的工程问题了，而且，还给以后想再接入更多种类的终端，比如平板、可穿戴设备什么的，把横向扩展的余地也留了出来。
上面说的这两条链路，在通信语义上，是严严实实给分开的，REST 通道扛的是强一致性的数据同步，WebSocket 通道扛的是实时性要求高的事件通知，然后，它们再一起靠着那个公用的数据库，去把最后的状态给校准一致，完成这样的流程后，就相当于构成了一个完整、能自己闭环转起来的端云协同框架了。
3.1.3 分布式同步通道设计
跨端协同同步通道的设计目标，是在多设备环境下提供与 HarmonyOS 分布式软总线语义等价的状态同步能力，同时规避真机直连软总线对同账号、同局域网与原生硬件的强约束，从而在更广泛的工程环境中复现"超级终端"的协同体验。
同步通道整体采用**"订阅—广播—持久化"的三段式发布-订阅模型，端到端协同流程如图 3-2所示。

当用户登录成功了之后，每个客户端节点都会朝那个同步事件中转服务，发出一个 subscribe 请求，这个请求里面，会带上用户标识 userId，还有设备标识 deviceId。中转服务这边一收到这个订阅，就会做两件事：一个是往 collaboration_active_devices 这张表里，写入或者更新一下这个设备的在线记录；另一个呢，就是用一个叫  HYPERLINK "https://device.online/" \t "https://chat.deepseek.com/a/chat/s/_blank" device.online 的事件，把它广播给同一个账号下面的其他那些已经订阅了的节点。那么，随便哪个节点，要是因为业务上有了变化，比如音乐播放状态变了、联系人更新了、或者有人发起了续接请求，就需要触发一次同步，这个时候，这个节点会先通过 REST 通道，把数据持久化掉，然后，后端的控制器再用 broadcastEvent 把这个事件推送出去，给到所有的订阅者；接收的那个节点呢，会按事件类型、对照着业务模块做一下过滤，再去更新自己本地的那个视图模型。
为了让系统跑起来更可靠，也方便出了问题能查得清楚，我们在这个通道上头，又额外加上了三项辅助性质的机制：第一个呢，是心跳和自动重连的功能，客户端那边有个单例服务，会在连接不小心断开的时候，按照一种指数退避的策略，也就是让重试的间隔时间慢慢拉长，去把会话给重新建立起来；第二个，是一张专门用来记同步操作日志的表，叫 collaboration_sync_logs，有了它，就可以对每一次的写操作，做那种行级别的追溯了；第三个，是一个抽象出来的接口层，它把客户端这边关于事件的订阅、发布这些操作，都给收拢到了一个叫 CollaborationSyncSocketService 的单例里面去，这么一来，以后要是想切到 HarmonyOS 原生的分布式数据对象，或者换成软总线的 RPC，就只需要把这一层的实现换掉就可以了，业务代码那边根本用不着改，这也算是给方案的下一步演进，保留了一条比较清楚的路径。

3.3.1 概念结构设计（全局 E-R 图）

3.4 详细设计
3.4.1 全局交互路由引擎
全局交互路由引擎是本系统在"非阻断式快捷交互"创新点之下的核心设计单元，其职责是将来自常驻全局层的用户操作意图，经由统一的事件总线分发至对应的业务模块，并保证主任务上下文不被中断。引擎的整体工作流程如图 3-5 所示。
图 3-5 全局交互路由引擎流程图
center0
这个引擎之所以能做到“非阻断”，主要靠的是在三个关键地方做的设计：第一个，是覆盖层那种呈现方式，所有次要任务的面板，都是直接覆盖在主界面的上头给显露出来的，这样底下那个主任务，它渲染的状态就不会被销毁掉；第二个，是用事件总线来把模块跟界面给解开，也就是靠 GlobalAnnouncerService 来当那个统一中转站，一搞起来，UI 层就完全不用去管具体模块里头是怎么实现的了；再一个呢，是一种延迟执行的路子，就是说，如果操作要找的那个目标模块，当时并不在前台，这个操作的意图就会先以 AppStorage 里一种状态的形式，暂时寄存在那里，等用户自己切到那个模块的时候再去真的执行，这么一来，也就彻底不会因为硬生生地去跳转路由，把视觉上给一块块打断了。
3.4.2 分布式数据同步机制（时序图）
分布式数据同步机制以 3.1.3 节给出的发布-订阅模型为基础，覆盖设备上线、续接发起、事件广播、续接执行、状态回流五个阶段，端到端的同步时序如图 3-2 所示（以"手机端将正在播放的歌曲续接到车机端"为典型场景）。
该机制具有以下三个工程特性：
(1) 以服务端为权威状态源。 所有写操作必须先经 REST 通道下沉至 MySQL，再由后端通过 WebSocket 通道广播事件，从而避免"本地写入成功但同步失败"导致的状态分裂。该设计在工程上等价于一个轻量级的最终一致性协议。
(2) 事件按用户域过滤。 CollaborationSyncHub 在 broadcastEvent 时仅向同一 userId 的连接广播，并在事件信封中附带 targetUserId 与 sourceDeviceId，客户端据此完成幂等去重与权限校验，从源头上杜绝跨账号信息泄露。
(3) 业务流程对网络容错友好。 所有客户端请求均设有超时与重试策略；WebSocket 连接断开后由客户端单例服务按指数退避重建会话，重建后通过 REST 接口重新拉取一次全量状态，从而以"轮询兜底 + 推送加速"的方式同时获得实时性与可靠性。
3.4.3 非阻断式交互调度
非阻断式交互调度这个东西，本质上就是 3.4.1 节里头那个路由引擎在真正跑起来的时候，用来管事儿的一套执行策略。它要解决的核心问题说白了也挺直接，就是当好几个次要任务的面板，它们的唤起请求一下子同时涌过来的时候，怎么才能在让用户感觉不乱的前提下，别让覆盖层在视觉上叠成一团，也别把主任务那边的画面给搞得一卡一卡的。本系统给出的这套调度策略，正如图3-6 所示。

第四章 系统实现
4.1 关键算法实现
4.1.1 全局非阻断式快捷交互的实现逻辑
全局非阻断式快捷交互这部分，在具体做工程实现的时候，是拆成了两块来搞的：入口那一侧呢，就是放在全局快捷条里的UI控件，它要干的事儿，是负责把用户想要干什么的那个意图给拿到手；调度这一侧呢，就是由一个单例服务，也就是GlobalAnnouncerService，来担着了，它要管的事情，是把那些协同的事件按照不同的类型给分出去，并且想办法用最小的代价去把视图给更新一下。这个服务的实现，代码是搁在了 entry/src/main/ets/services/GlobalAnnouncerService.ets 这个文件里，整个写下来，大概也就150行的样子。
服务在应用刚刚启动那一下，会由 EntryAbility 来调用它里面的 init()，把初始化的活儿一次性给干完，这里对应的代码在 GlobalAnnouncerService.ets 的62到69行。具体来讲呢，会先通过 bootstrapBackend() 把端跟云那边后端的配置给拉通；接着呢，是把同步事件的监听器给注册到 CollaborationViewModel 上去，这样一来，所有那些由后端给广播下来的协同事件，就都能统一地汇到本服务的 handle(event) 这个入口里头来。至于设备角色的判定这一套逻辑，也是在初始化这个阶段就一道做完了，它的策略是，先去读 AppStorage.collab.role 那个地方有没有人为指定好的角色，有的话就先用着；要是没有呢，那就退一步，按照 deviceInfo.deviceType 去自动判断一下，是给标成 phone-001 还是 car-001，这么一来，也就相当于搞出了一个在调试时可以手工切换、而在真正跑起来时又能自己去识别的双模式，这块的代码，大致是在71到95行那一片。事件分发的核心算法如下：
算法 4-1 全局事件路由分发
（对应实现：GlobalAnnouncerService.handle，文件 GlobalAnnouncerService.ets:97-149）
输入：协同事件 event {type, sourceDeviceId, payload, timestamp}
输出：无（副作用：写 AppStorage / 触发 TTS）
1. 令 myId ← 当前设备标识
2. 如果 myId ≠ 'car-001'，直接返回 // 仅车机端承担常驻广播
3. 如果 event.sourceDeviceId == myId，直接返回 // 自源事件去重
4. 分支：根据 event.type 选择处理路径
4.1 case 'message.created':
从 payload 取 threadId / name / preview
如 threadId == lastSpokenId 则返回 // 同条短信不重播
更新 lastSpokenId ← threadId
调用 TTS.speak("收到一条来自" + name + "的短信...")
返回
4.2 case 'music.handover':
从 payload 取 songId / position / target
如 target ≠ myId，返回 // 非本机的续接请求忽略
构造 PendingMusicHandover 对象
调用 AppStorage.setOrCreate('pendingMusicHandover', pending)
调用 TTS.speak("收到来自手机端的音乐续接申请...")
返回
4.3 case 'navigation.handover':
类似 4.2，写入 AppStorage 'pendingNavHandover'
触发 TTS 公告
返回
该实现的两个工程亮点：第一，通过将"待确认续接请求"以 AppStorage 形式驻留，使车机端无须事先打开协同模块即可"被动接收"来自手机端的续接申请，由 @StorageLink 在协同页面按需读取，从而避免了"必须先进入页面才能收到"的耦合问题（详见 GlobalAnnouncerService.ets:122-129 与 142-144 的注释）；第二，自源事件过滤（第 3 步）保证了同一台设备发出的事件不会被自身再次处理，避免了广播回流导致的状态抖动。
4.1.2 歌词时间轴解析与翻页对齐算法
歌词模块这边，得接连搞定两个问题：头一个呢，是把磁盘上存着的.lrc文本，给解析成能按索引去查的时间跟文本凑成对的那种形式；第二个，就是在播放进度往前跑的时候，怎么用最省事儿的办法，把“当前这句给高亮出来，同时上下那些行像卷帘子一样跟着平移”这个效果给做出来。实现的代码呢，放在了 entry/src/main/ets/view/MediaModule.ets 这个文件里头，起关键作用的两个函数，一个是 parseLrc()，大概在 691 到 725 行那一片，另一个是 getRenderedLyrics()，在 770 到 786 行那块。
标准的 LRC 格式，它本身是这样的，就是 [mm:ss.xx] 后面再跟上 <歌词文本>，而且同一行歌词，有可能会绑着好几个时间戳，这主要是用在副歌那种会重复的段落上。本系统用的解析算法，思路大致如下：
算法 4-2 LRC 时间轴解析
（对应实现：MediaModule.parseLrc，文件 MediaModule.ets:691-725）
输入：LRC 文本 content
输出：时间升序排列的歌词行数组 lines[{time, text}]
1. 令 offset ← 0
2. 若 content 包含 '[offset:N]' 头，更新 offset ← N
3. 令 timeRe ← /\[(\d{1,3}):(\d{1,2})(?:[.:](\d{1,3}))?\]/g
4. 按行分割 content
5. 对每一行 raw 执行：
5.1 令 stamps ← []
5.2 循环执行 timeRe.exec(raw)：
5.2.1 提取 min, sec, frac
5.2.2 将 frac 标准化到 3 位毫秒（"xx" → "xx0" → 整数）
5.2.3 ts ← min×60000 + sec×1000 + frac + offset
5.2.4 stamps.push(ts)
5.3 令 text ← 时间戳之后的文本（trim 后非空）
5.4 对 stamps 中每个 ts，向 lines 写入 {time:ts, text}
6. 按 time 升序对 lines 排序
7. 返回 lines
跟那些开源的 LRC 解析库比的话，本算法在实现的时候，其实是特意留着三个工程上的考量没有丢掉：第一点，就是那个毫秒补零的步骤（5.2.2 里说的），这么做主要是为了能兼容 LRC 文件里头很常见的、把毫秒只写成两位的那种缩略情况；第二点呢，是把多时间戳给分裂展开（对应 5.4 的做法），这样一搞，等到了卷帘对齐那个阶段，就可以直接拿二分法去找了，不用再费劲去处理里面那些嵌套起来的结构；第三点，就是最后的那个全局排序（第 6 步做的），这个是为了保证那些属于副歌的段落，在被合并、展开完了之后，它在时间顺序上还是单调的、不乱，这才能让下一个阶段里那个定位的算法，不至于跑出毛病来。
至于翻页对齐这块，用的是让单个容器保持不动、靠着整体平移来解决的策略，具体说呢，就是所有的歌词行，都是给渲染到一个固定住了高度的容器里头去的，活动的那一行，就让它时时刻刻都待在容器的正中间，然后靠着给这整个容器加上一个 translateY 的偏移量，把“当前行”给卷到中心那个位置上去，行跟行之间，并不去把组件销毁了再重新创建一遍，只是拿 ArkUI 里的 @State 来触发一次增量的重新渲染，就把事儿给办了。这个算法，可以这么来描述：
算法 4-3 歌词卷帘对齐
（对应实现：MediaModule.getRenderedLyrics + computeActiveLyricIndex + updateLyricTranslate
文件 MediaModule.ets:770-786 等）
输入：当前播放时刻 currentTime
输出：渲染列表 rendered[{time, text, isActive}] 与容器位移 dy
1. 令 lyrics ← 当前曲目的歌词数组
2. 若 lyrics 为空，返回 [{0, '暂无歌词', true}]，dy ← 0
3. 令 activeIndex ← 0
4. 对 lyrics 中每个 line（按时间升序）：
4.1 若 currentTime ≥ line.time，activeIndex ← 当前下标
4.2 否则跳出循环
5. 对 lyrics 生成 rendered，第 activeIndex 行 isActive=true
6. dy ← (CONTAINER_CENTER_Y) − (activeIndex × LINE_HEIGHT)
7. 返回 rendered, dy
这个算法在复杂度上，也就是 O(N) 这么一个水平，对于常见的 LRC 文件来说，它们典型的行数也就 50 到 150 行左右，所以完全可以在一次播放的回调里面就把它给跑完；要是遇着那种歌词特别长的情况呢，也可以在第 4 步那里，把它给换成一种基于上一帧 activeIndex 的局部线性扫描，或者直接用二分查找的办法，这样一来，就能把开销进一步地给降下去了。

4.2 分布式多设备协同实现
4.2.1 设备发现与在线状态维护
设备发现是跨端协同的入口环节，本系统不依赖局域网组播或鸿蒙原生设备发现 API，而是以同账号订阅为发现协议：当任一客户端登录成功后，由 CollaborationSyncSocketService 主动建立 WebSocket 连接并发送 subscribe 请求；服务端 CollaborationSyncHub 在收到订阅后将该设备 upsert 至 collaboration_active_devices 表，同时向同账号下所有已订阅节点广播 device.online 事件。该协议的服务端实现位于 d:\Users\47346\DevEcoStudioProjects\huawei/backend/src/services/collaborationSyncHub.ts:40-100，伪代码如下：
算法 4-4 设备发现与在线状态维护（服务端）
（对应实现：collaborationSyncHub onConnection / onMessage / onClose
文件 backend/src/services/collaborationSyncHub.ts:40-100）
输入：来自客户端的 WebSocket 帧
输出：collaboration_active_devices 表的最终一致状态 + 设备上下线广播
OnConnection(socket):
1. send(socket, {type:'connected', timestamp})
OnMessage(socket, message):
1. 解析 message 为 {type, userId, deviceId, event}
2. 若 type == 'subscribe':
2.1 subscribedClients[socket] ← {userId, deviceId}
2.2 send(socket, {type:'subscribed', userId, deviceId})
2.3 record ← upsertActiveDevice(deviceId, userId)
2.4 broadcastEvent(createSyncEvent('device.online',
{deviceId, role:record.role, userId}))
3. 若 type == 'sync' 且 event 存在:
3.1 broadcastEvent(event)
OnClose(socket):
1. info ← subscribedClients[socket]
2. delete subscribedClients[socket]
3. 若 info 非空:
3.1 markDeviceOffline(info.deviceId)
3.2 broadcastEvent(createSyncEvent('device.offline',
{deviceId:info.deviceId, userId:info.userId}))
这个协议在工程实现上，用起来有三个比较好操作的优势：首先呢，它是把“设备在线”这个状态，用数据库里一行记录的形式给存下来的，这样一来，就算有一台客户端是在协同页面打开之前就已经完成了订阅，其他客户端也照样能通过查一下 /api/v1/collaboration/devices 这个接口，知道它的角色跟上线时间；其次，当连接断开的时候，是由服务端而不是客户端，去负责把那个“标记下线”的动作给做了，这样就能避开因为客户端那边异常退出，导致状态留在那里清不掉的麻烦；再者说，role 那个字段，是靠着 device-id 的前缀，也就是 phone-* 或者 car-* 这样子，去判断出来的（这块在 init.sql 的 132 到 141 行注释里头有写），这么一来，前端那边要区分哪个是本机、哪个是对端，就很容易了，也不用再去走一套额外的授权流程。
4.2.2 WebSocket 双向同步通道
同步通道在客户端这边的实现，代码都放在了 entry/src/main/ets/services/CollaborationSyncSocketService.ets 这个文件里头，它是做成了单例的模式，把 HarmonyOS 系统自带的那个 @ohos.net.webSocket 模块给包在了里面，然后对外头呢，就给出了 connect、addListener、emit、close 这么四个公共的 API 可以用来调用。
等连接建好了之后，客户端会先发一个 subscribe 报文出去，这个在文件的大概 48 到 68 行那里；当 message 这个回调被触发的时候，它会按照 sync-event 这种事件的类型去做解码，接着再通过监听器的那个队列，把消息分给各个业务模块去处理，这块的代码在 69 到 82 行左右；而万一碰到了 close 或者 error 这样的事件，就会进到一个断线重连的流程里头去，代码是 83 到 92 行那一片。重连这套策略的伪代码，大致是下面这么个思路：
算法 4-5 客户端断线重连（指数退避）
（对应实现：CollaborationSyncSocketService.scheduleReconnect
文件 CollaborationSyncSocketService.ets:101-114）
输入：连接异常事件
输出：在 manualClose=false 的前提下重新建立长连接
1. 若 manualClose 为真，直接返回
2. 若 reconnectTimer != -1（已有计时器在等待），返回
3. reconnectTimer ← setTimeout(after 3000 ms, 执行步骤 4..7)
4. reconnectTimer ← -1
5. 若 manualClose 为真 或 connected 为真，返回
6. 若 client 与 url 均存在：
6.1 client.connect(url, _) // 复用已有 client，不重建
7. 否则忽略本次重连
现在这个实现里头，重连那边的等待间隔，是给写死了的3秒钟，这么搞主要是为了在录视频演示的时候，连接能稳当一点，不会乱闪；假设后面要把它拿到真实环境里去跑的话，其实就可以在第3步那个地方，把 3000 ms 这个值给换成 Math.min(30000, 1000 * 2^retryCount) 这么一个算法，用这种指数退避的路子来弄，我们呢，也为后面真要这么改，在源码里事先留好了一个挺清楚的、方便下手去改的位置。
服务端的事件分发由 broadcastEvent 完成（collaborationSyncHub.ts:103-119），其按"同 userId 域"过滤的伪代码如下：

端到端流程的工程要点：第一，所有写操作先经 REST 通道下沉至 MySQL 再由 SyncHub 广播，保证"持久化先于通知"，杜绝了"通知到达但落库失败"的错乱状态；第二，车机端通过 AppStorage 暂存待确认请求，使用户拥有充分的"确认权"，避免了未经用户允许的强制接管；第三，车机端在执行成功后回写 music.stateChanged 事件，由后端再次广播至手机端，从而触发手机端自动暂停，形成"接管闭环"。
4.3 基础业务模块实现
4.3.1 导航模块：高德地图集成与路径规划
导航模块基于 Web 组件加载托管在本地 rawfile/amap.html 中的高德 Web 地图 JavaScript API，并通过 ArkTS 与 H5 之间的 JavaScript Bridge 完成双向调用，相关实现集中在 entry/src/main/ets/services/AmapService.ets 与 entry/src/main/ets/view/EnhancedNavigationModule.ets 中。模块整体采用"WebView 承载渲染 + ArkTS 承载状态"的桥接模式：H5 侧专注于地图的可视化、路径绘制与 POI 渲染；ArkTS 侧承担用户输入采集、收藏与历史的本地与云端持久化、地图回调事件的反序列化等。
这个模块对外提供的能力，大致能分成三个核心的方面：一个是 POI 的关键字检索，这块是依托高德地图的 AMap.PlaceSearch 来做的，用户输进去的关键字，会被转换成带有经纬度信息的候选项；再一个是路径规划，它依靠的是高德的 AMap.Driving，会把当前定位当成起点，往选中的 POI 那里去规划出一条开车的路线，并且在地图上用一条高亮的折线给画出来；还有一个呢，是收藏和历史记录的持久化，每次路径规划成功之后，就会通过 REST 通道，向后端的 /api/v1/navigation/history 这个接口写入一条历史记录，这条记录最终是给存到 navigation_history 这张表里去的（这块可以看 3.3.2 节的表 3-3）。这三类能力的代码，都是靠着一套统一的 postMessage 报文协议，在 ArkTS 跟 H5 之间传来传去的，这么一来，就避免了把地图组件内部的状态泄露到上层业务那边，形成一种反向依赖的情况。另外呢，这个模块还会在路径规划一做成功的时候，通过 RealTtsService 去触发一句语音播报，播的内容大概是“已为您规划路径，即将出发前往 ⟨目的地⟩”这个样子，这个做法，和 4.1.1 节里提到的那个全局非阻断式快捷交互的理念是配得上的——也就是，驾驶员这边根本用不着把视线从主任务上挪开，就能知道路径已经给规划好了。
4.3.2 多媒体模块：本地音频与歌词同步
多媒体模块这部分，是拿 HarmonyOS 系统里自带的 @ HYPERLINK "https://ohos.multimedia.media/" \t "https://chat.deepseek.com/a/chat/s/_blank" ohos.multimedia.media 那个 AVPlayer 来搭的，主要负责本地音频的播放控制这一块；同时呢，又把 4.1.2 节里头说的那个 LRC 解析和卷帘对齐的算法给叠了上去，这样歌词同步显示的事儿也归它管了。整体实现的代码，基本都集中放在了 entry/src/main/ets/view/MediaModule.ets（大概有 1600 行的样子）跟 entry/src/main/ets/services/RealAudioPlayerService.ets 这两个文件里头。
在工程上，这个模块有三个比较关键的设计点：第一个，是关于资源和歌词的协同加载，曲目的元数据里头，是用 rawfile:sample_music_N.mp3 这么个标识来指明音频资源的路径的，模块在加载曲目的时候，会拿 loadLyricsForItem() 这个方法，自己根据这个路径推导出一个同名的 .lrc 文件，然后试着从 rawfile 那个目录里给读出来（这部分的处理在 MediaModule.ets 的 731 到 768 行），要是没找着这个文件，它也不会报错，而是默默地退回去，用代码里写死在那儿的硬编码歌词，这就保证了在最差的情况下，界面上还是能正常显示出东西来，不会空着。第二个设计点，是靠渲染版本号来驱动，LRC 解析一做完，就把 this.lyricLoadedVersion 这个值给加个一，用这种办法去强制让 ArkUI 重新渲染一下，这么做的目的，是为了解决 ArkUI 里 ForEach 组件在发现依赖的东西没变时，会自己跳过重渲，导致“歌词明明已经解析好了但界面就是不显示”这种问题，这块代码在 MediaModule.ets 的 745 到 747 行附近。第三个，是保证主播放线索的单一性，AVPlayer 的 timeUpdate 那个回调，是整个模块唯一的时间源头，歌词应该在什么位置、进度条走到哪儿了、还有需要往对端上报续接状态这些事儿，全都是被这一条线给牵着走的，这样就能避开因为好几个时间源头不同步，带来的那种视觉上抖来抖去的毛病了。
4.3.3 车辆监控模块
车辆监控模块，它的目标车型选了电动车，靠着模块里头自己带着的一个双频采样模拟器，实时地去把车速、动力电池、胎压还有温度这些最核心的指标给驱动起来，所有实现的代码，全搁在了 entry/src/main/ets/view/CarStatusModule.ets 这个文件里，整个写下来，差不多有622行。
这个模块在最核心的算法上，用的是一个叫双频采样的调度办法，具体来讲，就是把要采的指标给分成了高频跟低频两类来处理：像车速、电量那种很细小的变化，再加上心跳的节拍这些属于高频的指标，采样的间隔给设成了100毫秒，主要是为了保证仪表盘这边看起来能有个流畅的刷新率；另一边呢，像续航、舱内车外电机那三个温度、胎压、ECO评分、还有累计里程以及最近七天那个柱状图这些，就归到低频指标里去了，它们采样的间隔就给拉长到了2000毫秒，这么做的道理，是为了躲开因为高频重绘带来的、不必要的GPU负担，这块的逻辑在 CarStatusModule.ets 的51到73行那儿能看到。这套策略搞起来的伪代码，大概是下面这个样子：

4.4 本章小结
这一章，主要是围绕着系统在工程上到底是怎么一步步给做出来的，展开了去讲。在关键算法这块，先是把全局非阻断式快捷交互里那个事件路由分发的算法，也就是算法4-1，给交代了一下，然后是LRC时间轴的解析和歌词卷帘对齐这两个算法，分别对应算法4-2和算法4-3，再就是把跨端续接这件事抽象成的有限状态机，用图4-1给画了出来；同时呢，在表4-1里头，还把状态机的每一次迁移，都明明白白地对着代码仓库里的具体位置给锚定了下来。到了分布式协同这个层面，讲了设备的发现协议（算法4-4）、客户端在断线之后的重连策略（算法4-5），还有服务端那边怎么按用户域做广播（算法4-6），并且用图4-2，把从手机到后端再到车机，这么一整趟协同续接的端到端时序，完整地给呈现了出来。接着基础业务那层，则是分别对导航模块里头的桥接模式、多媒体模块怎么去做资源跟歌词的协同加载，还有靠着渲染版本号来驱动的那个机制，以及车辆监控模块用的双频采样调度（算法4-7），都分别做了描述。里头所有给出的伪代码，都清清楚楚地把对应的文件路径跟行号范围给标了上下，每一个工程上的结论，也都是能在仓库的源码里头去核实的。这一章最后得出来的这些实现，算是给第五章要开展的功能测试、性能测试还有协同测试，提供了能把它们跑起来的那个可以执行的工程对象了。

5.2 测试方法
5.2.1 测试策略
在测试策略上，本系统用的是以黑盒测试为主，再拿白盒测试来当辅助，这么一种搭配起来的办法，黑盒测试这块，是把用例当成基本单位，从用户使用的角度去核实业务行为是不是跟预想的一样，主要用在功能测试上；白盒测试呢，则是把代码路径拿过来当单位，对着4.1.2节里LRC解析那部分、4.1.3节里的续接状态机迁移，还有4.2.2节里头那个断线重连的分支，去做覆盖式的调试，主要就是在性能测试和边界条件的测试上用到它。5.2.2 测试用例设计原则
功能测试的用例在设计的时候，遵循的是等价类划分、边界值分析再加上错误推测这么三条原则，具体来说呢，一个是对每一项功能，都要最少设计出一组正向的用例，也就是典型的有效输入那种，和一组反向的用例，也就是典型的无效输入或者是异常分支那种；再一个，碰到跟数值范围有关的输入，像位置、坐标还有时间戳这些东西，就会去挑一些比较典型的边界值来测；还有一个呢，就是遇到跟网络、并发有关的功能，会再补上网络中断、重连、多个请求同时触发这一类容易出错的场景。
5.2.2 性能与协同测试方法
性能测试这块，是用DevEco Profiler这个工具来采样的，采样的区间，是从应用冷启动开始，到它稳定跑上60秒为止，CPU和内存的数据，是按1秒钟一次的粒度来采，FPS则是按ArkUI渲染帧的粒度去采。协同测试这边呢，用的是一种“客户端发出时间戳，服务端再把它转发出去，最后看接收端时间戳”的三点法，来测量同步的延迟，每个事件类型都连着测上50次，然后取它们的算术平均值，还有P95分位数。

5.4 性能测试（FPS / CPU / 内存）
5.4.1 测试目标与方法
性能测试这一块，要验证的东西说白了就是，系统在平常跑起来的时候，能不能够达到2.3.2节里提的那些非功能性需求，主要盯着看的是四个指标：冷启动的时长，也就是从应用进程开始启动，到主页面首屏渲染全部完成所用的时间；渲染的帧率FPS，就是主要界面在正常滑动或者切换时，帧率的一个均值；CPU的占用率，取的是应用进程在常态运行下面，CPU占用的平均值和峰值；还有就是内存占用，看的是应用进程常驻的RSS内存有多大。
测试的方法是这么搞的：先用DevEco Profiler这个东西启动一个60秒的采样窗口，把应用从冷启动到稳定运行这整个链路都给包进去，CPU和内存的数据，就按每1秒钟采一次的粒度来抓，FPS呢，是顺着ArkUI实际渲染的帧来采样；然后每一项指标，都会在三种比较典型的场景底下，也就是导航主任务那种情况、媒体播放加上歌词卷帘一块儿跑的情况、还有车况双频采样的情况，分别测上3次，最后取一个算术平均值出来。

5.5 协同测试（同步延迟 / 续接成功率）
5.5.1 测试目标与方法
协同测试的目标，就是要对跨端同步这条链路，在两个最关键的质量维度上，给出一个量化的结果，一个是看同步延迟，也就是一个事件从源设备这边被触发，到另一边目标设备上真有反应了，这中间端到端总共花掉的时长；另一个呢，是看续接的成功率，也就是在好多次续接尝试里面，成功的比例到底有多少。
同步延迟的测量，用的是那种三点法来做，大概的思路是：客户端这边，会在要发出事件（也就是emit）的时候，把那个时刻记成t1；等事件到了后端，在broadcastEvent那一下子把t2给记下来；最后在接收端真正处理事件（也就是handle）的时候，再记一个t3。这么一来，就能用它来算延迟了，端到端的延迟就是t3减t1，后端转发花了多久就是t2减t1，客户端接收这边又耗了多少则是t3减t2。为了让结果能稳当点，每种事件类型呢，都被来回测了50遍，然后把平均值和P95分位数这两个数都给算了出来。测试里牵涉到的事件类型，包括了 HYPERLINK "https://device.online/" \t "https://chat.deepseek.com/a/chat/s/_blank" device.online、message.created、music.handover、navigation.handover还有music.stateChanged。
续接成功率的测量，方式是，在手机跟车机都已经确认都订阅上了的状态下，从手机那一端，一连气地发起50次音乐的续接操作，再来50次导航的续接操作，然后就统计一下，车机这边是不是能在5秒钟这个时间里面，按照要求把事儿给办成了，对于音乐来说，成功就是能 seek 到目标位置开始播放了；对于导航呢，就是地图上能正确地显示出来目标终点的路径，最后看这个成功的次数占总的次数是个什么比例。

第六章 结论
6.1 工作总结
本课题以 HarmonyOS 为底层平台，围绕"分布式的内核 + 极简的交互外壳"这一总体设计理念，研究并实现了一套面向智能座舱场景的车载信息娱乐系统。论文的全部工作可归纳为以下四个方面。
第一，是把系统从头到尾的工程构建给完整地走了一遍。论文最开始是从产业背景和文献综述那块起步的，然后顺着往下，把业务分析、可行性论证、需求建模、概要设计、详细设计、模块实现，再到系统测试，这么七个工程阶段，一个接一个地都给做完了，最后呢，等于是搭起了一个基于六层垂直分层架构的、完整的工程闭环；其中，系统的应用层被细化成了五大模块，加起来一共27个功能子单元，把车载场景下面导航、多媒体、车辆监控、多设备协同还有账号身份这五类核心业务，全都给覆盖到了。
第二，是把那个全局非阻断式的快捷交互机制给做了出来。论文里头，是拿 GlobalAnnouncerService 这个单例服务来当最核心的中枢，再拿 AppStorage 里的全局响应式状态来当一层缓冲，入口的控件则是放在了全局快捷条上，靠着这些，最后构建出了“覆盖层呈现、事件总线分发、再加上延迟执行”这么一套复合的调度策略。靠着这个机制，驾驶员在开车状态下，去处理那些次要任务时，视线偏离路面的时间跟操作的步数，都能被压到一个很小的范围里头，这跟车载HMI在驾驶安全约束下那些典型的设计准则是能对上号的[8]。
第三，是搞出了一个基于发布-订阅模式的、跨端数据同源的同步通道。论文在并没有去依赖 HarmonyOS 原生分布式硬件环境这个前提底下，是借鉴了软总线跟分布式数据服务的那套语义模型[5][6]，然后在应用层，自己搭出来了一条三段式的同步通道，这条通道是以服务端的 CollaborationSyncHub 作为中枢，拿 WebSocket 长连接来当传输的通道，再拿 MySQL 的集中持久化来作为状态的基线，并且，还靠着设备发现协议、按用户域过滤的事件广播、断开后自动重连这些配套的子机制，把通道的可用性和安全性都给保住了。在工程上，这条通道算是把“音乐续接、导航续接、短信广播”这些最核心的协同语义，都给完整地复现了出来。
第四，是把系统的功能、性能还有协同这三方面的测试给做完了。论文在第五章里头，是设计出了覆盖三大创新点的10项核心功能用例、6项关键的性能指标，还有针对5类同步事件的端到端延迟测量方案，并且给出来了一套完整的测试矩阵跟测量方法。
6.2 研究成果与社会、经济、文化关系
本课题的研究成果与社会、经济、文化三个维度均存在密切关联。
在社会这个维度上，本课题提出的那个全局非阻断式快捷交互机制，说到底，就是在拿软件工程的那些办法，去试着给驾驶分心这个挺现实的社会问题开一点药方。现在开车那个环境底下，车载次要任务的数量跟复杂程度，是一直在往上走的，因为处理这些次要任务而引起的“那么一瞬间的视线偏离”，已经成了城市道路交通事故里头一个绕不开的重要诱因了。而我们这个系统，是把次要任务从原来那种层级菜单和页面来回跳转的操作里给摘了出来，在不硬生生打断主任务的情况下，就把切换的事儿给办了，这么一来，客观上应该是能把驾驶员在注意力分配上的压力也给拉下来一些的，对于帮着把道路交通的安全性往上提一提，多多少少是有它正向的社会意义在里头的。
在经济维度，本课题以国产操作系统 HarmonyOS 为开发平台，所有依赖的开发工具与软件组件均为开源或国产商用产品，研发与运维成本可控；同时，本课题所验证的"经云端中转的发布-订阅协同"工程范式，为车企在不依赖完整鸿蒙原生分布式硬件环境的前提下，于现有车机平台上落地"上车续看、下车续听"等连续性体验提供了可参考的工程原型，有助于降低相关功能的工程门槛与产业化成本。从更长远的视角看，国产车载操作系统及其上层应用的成熟，将进一步带动智能座舱产业链的本土化与规模化发展，孕育新的商业模式与就业机会。
到了文化这个维度，本课题算是国产操作系统在智能交通这个垂直领域里，做的一次工程实证了，它工程上头的意义，倒不单单是说最后交出了一个完整的车载信息娱乐系统，那个还在其次，更要紧的地方在于，它用了一种可以复现出来的方式，去展示了国产软件生态在像复杂工业应用这种场子里，是能干得成事儿的，也是有竞争力的[10]。放到如今国产基础软件在长期寻求突破这么个大背景下面，这一类工程实证，是能帮着从业者还有社会上的大家，对国产技术多攒起一份信心的，而且，它也是拿“软件咱们自己能造、生态也真能建”这么一个活生生的例子，去回应了学界跟产业界那边长期关心的事儿。
6.3 主要创新点
把上面说的这些工作拢到一块儿看，本论文主要的创新点，大致能归纳成下面这三个方面。
创新点一，是搞了一个面向车载智能座舱的、把多个模块统一到一起的架构整合。之前分析过，现有的 IVI 在生态封闭、交互层级冗余，还有多设备协同困难这三个地方，是存在着结构性的短板的，本论文就在这个分析的基础上，提出来一套工程范式，并且把它给做了出来，也就是把导航、多媒体、车辆监控和多设备协同这四个大模块，在 HarmonyOS 的那套六层垂直分层架构底下，给统一地整合到了一起。这套范式，拿“层次之间单向依赖、再加上接口耦合”来当成基本原则，这样一来，就绕开了那种只是把功能往上堆砌的 IVI 在慢慢演进的过程中，很容易碰到的模块之间互相侵入的那么些个毛病，也算是给后面相关的工程实践，拿出了一个可以参考着用的架构模板。
创新点二，是提出了一套面向驾驶场景的、视觉和听觉两条通道一块儿走、还不会打断主任务的交互范式。跟以往那些 IVI 还在沿用桌面端和移动端“层级菜单加上页面跳转”的交互模型不一样，本论文提出的这种非阻断式的交互范式，是把视觉和听觉这两条通道并行着来搞的：在视觉这条通道上，用的是“覆盖层、全局事件总线、再加上智能布局”这么一套复合的机制，把次要任务的切换路径，给压缩成了在常驻全局层上的一次轻轻的操作，主任务那边跑着的上下文，并不会被打断；在听觉这条通道上呢，是把 RealTtsService 拿来当统一的一个抽象层，碰到路径规划做完了、协同短信到了、跨端续接的申请发过来了这类比较典型的时候，就会主动用语音播报的方式，把状态的变化给推送出去，让驾驶员能在视线不离开路面的情况下，就能把系统的状态给感觉到了。这两条通道，是靠 GlobalAnnouncerService 这个单例服务，给统一调度的，而 AppStorage 里头那些全局的响应式状态，专门用来扛跨模块的状态共享，再那个面板状态机的调度策略，来保证多业务一块儿挤过来的时候，视觉上能一直维持着节奏，这么些个东西加到一块儿，就成了本课题在车载 HMI 范式这个层面上的具体探索了。
创新点三，是建了一条能适应异构网络环境的、跨端数据同源的同步通道。跟已有的那些研究里头，大多是拿单一垂直的业务，比如光一个音乐播放这种，去当成对象来验证分布式协同[7]的做法不一样，本论文是搞了一套统一的同步通道出来，这个通道能把音乐、导航、联系人、短信，还有设备状态这五类不同性质的业务，全都给包进去，并且，靠着“先做持久化再去通知、按用户域来过滤广播、客户端那边再根据需要自己重连”这么三重机制，保证了在多业务并发的情况下，同步语义依然是对的，通道也一直是能用的。这条通道，在并没有去依赖 HarmonyOS 原生分布式硬件环境的这个前提底下，就在应用层，把 HarmonyOS 分布式协同最核心的那些语义给完整地复现了出来，这应该算得上是给相关的技术，在更宽泛的工程环境下落地的时候，提供了一个可以参考的工程原型了。
6.4 不足与未来展望
因为受到研究周期、硬件条件，还有课题本身边界的这些限制，本系统在下面这三块地方，说起来还是留着一些能继续往好里改的空间的。
不足之一，是车辆的数据源头，还只是个模拟器，并没有接到真实的 CAN 总线上去。主要原因，是拿不到真实电动车 CAN 总线的接入权限，硬件条件上也够不着，所以，本系统的车辆监控模块，就只能用一个双频采样的、内置数据模拟器，来顶替真实车辆传感器那边传过来的输入。这么实现下来吧，倒是把完整的数据通路跟可视化的能力都给留住了，但是，它到底也没能搁在真车那个环境下去验一验，看看那些算法在面对不同的采样率、噪声分布，还有一些异常的工况时，到底还扛不扛得住。
不足之二，是跨端协同这块，本质上是靠着 WebSocket 长连接撑着的，并没有用到 HarmonyOS 原生的那些分布式硬件能力。这主要是为了照顾部署环境上的兼容性，所以系统的同步通道，是在应用层那边去借鉴了软总线的语义，而不是直接去调 HarmonyOS 原生的分布式 API。这个搞法呢，虽然把最核心的协同语义给等价地复现出来了，但是，跟那种原生的分布式数据对象一比的话，在弱网环境下的容错能力，还有端发现的覆盖程度上，还是差着一截。
不足之三，是测试的规模跟覆盖的全面程度，都还挺有限的。本课题的功能、性能还有协同这些测试，全是在两台模拟器加上本地回环网络这么个环境底下跑完的，像那种跨地域、跨网段、好多个用户一块儿并发的大规模场景，就都没能覆盖到；而且，手头能用的音频资源，也就是 rawfile 里头内置的那三首样曲，跟真正实际用起来时那个曲库的规模比起来，差得也还挺远的。
针对上头说的这些不足，后续的工作，是可以试着从下面这三个方向再往下推动的。头一个，要是能跟车企，或者是那些开放的车载数据平台搭上线合作就更好了，然后靠着拿到的数据，把车辆监控模块从模拟器给切换到真实 CAN 报文的消费方上去，再根据真车跑出来的工况数据，对采样调度和可视化的算法，去做一轮二次的优化。第二个，是把那条同步通道，从现在的 WebSocket 实现，给迁移到 HarmonyOS 的分布式数据对象跟软总线RPC 上去，好在，因为 4.2.2 节里客户端的实现，早就用 CollaborationSyncSocketService 这个单例把接口给抽象好了，所以这个迁移在工程上，其实要动的地方很集中，就光是替换掉这一层的实现就行，上面的业务代码那边，一点都用不着改。第三个方向，是把这个系统往更多样化的终端形态上推，在手机跟车机之外，再试着把平板、能穿戴的设备、还有车里面后排的屏幕这些终端类型都纳进来，同时，把协同的业务，也从现在的这五类，给慢慢扩展到视频的续看、车控的指令、还有那种个性化的场景模式等等更复杂一些的业务上去，这样呢，本课题搞出来的这套“超级终端”的工程范式，就能朝着一个更全乎的智能出行生态，再往前多走一步了。

export async function login(req: Request, res: Response) {
  const { phone, password } = req.body;
  const users = await query<any[]>(
    'SELECT id, phone, password, nickname FROM users WHERE phone = ?',
    [phone]);
  if (users.length === 0 ||
      !(await bcrypt.compare(password, users[0].password))) {
    return res.status(401).json({ code: 401, message: '手机号或密码错误' });
  }
  const token = generateToken(users[0].id);        // 签发 JWT
  res.json({ code: 200, message: '登录成功',
    data: { userId: users[0].id, phone, token } });
}
A.3 鸿蒙端 HTTP 封装（HttpService.ets）
private async request<T>(method: http.RequestMethod, url: string,
    data?: Object, needAuth = true): Promise<ApiResponse<T>> {
  return new Promise((resolve) => {
    const req = http.createHttp();
    const headers: Record<string, string> = {
      'Content-Type': 'application/json'
    };
    if (needAuth && this.token) {
      headers['Authorization'] = `Bearer ${this.token}`;
    }
    req.request(`${ApiConfig.BASE_URL}${url}`,
      { method, header: headers,
        extraData: data ? JSON.stringify(data) : undefined,
        readTimeout: ApiConfig.TIMEOUT,
        connectTimeout: ApiConfig.TIMEOUT },
      (err, resp) => {
        if (err) {
          resolve({ code: -1, message: '网络请求失败' } as ApiResponse<T>);
        } else {
          const body = JSON.parse(resp.result as string) as ApiResponse<T>;
          if (body.code === 401) void this.clearToken();
          resolve(body);
        }
        req.destroy();
      });
  });
}
